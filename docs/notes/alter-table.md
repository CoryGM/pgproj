# `ALTER TABLE` in project SQL

`ALTER TABLE` in project SQL: `ADD COLUMN` (including `IF NOT EXISTS`, defaults, and inline constraints), `ADD CONSTRAINT`, and `ENABLE`/`DISABLE`/`FORCE`/`NO FORCE ROW LEVEL SECURITY` are applied, and the table and the statement may be in different files. `ALTER TABLE ... OWNER TO` is read as the table's owner (see [Owners](owners.md)). Any other `ALTER TABLE` action (`DROP COLUMN`, `ALTER COLUMN ... TYPE`, and so on) is reported as a warning by `build`, `diff`, and `publish` and is not applied, so declare the final shape of a table in `CREATE TABLE`.

**The forms `pg_dump` writes.** A project built from a `pg_dump --schema-only` file has these as `ALTER` statements, and they are applied as if `CREATE TABLE` or `CREATE SEQUENCE` had said them, in any file and in any order:

- `ALTER TABLE [ONLY] parent ATTACH PARTITION child FOR VALUES ... | DEFAULT`: the child becomes a partition of the parent, with the bound. A child that names a NOT NULL constraint other than its parent's is created with its columns and attached, so the name is kept (see [`NOT NULL`](not-null.md)); so is a child whose columns are in another order than its parent's, since `PARTITION OF` would give it the parent's order and PostgreSQL cannot reorder columns. Column order is still not compared: an existing partition is not rebuilt for it. A child written with its parent's order and no NOT NULL name of its own stays `PARTITION OF`, so on PostgreSQL 18 it takes its parent's NOT NULL names; to keep names of its own, state them.
- `ALTER TABLE ... ALTER COLUMN c SET DEFAULT expr` and `DROP DEFAULT`: the column's default (a serial column's `nextval(...)`).
- `ALTER TABLE ... ALTER COLUMN c ADD GENERATED { ALWAYS | BY DEFAULT } AS IDENTITY (options)`: the column is an identity, with its options as written.
- `ALTER TABLE ... ALTER COLUMN c SET STORAGE s` and `SET COMPRESSION m`.
- `ALTER SEQUENCE s OWNED BY table.column`: the sequence's owner column. A table written without its schema is the one the project's `searchPath` finds (`public` by default), as PostgreSQL resolves it, so it is the same as writing the schema; it is deployed as written. Any other `ALTER SEQUENCE` option is still reported and ignored.
- `ALTER INDEX parent_idx ATTACH PARTITION child_idx`, with `CREATE INDEX ... ON ONLY parent`: PostgreSQL makes a partition's index from the parent's, so the partition's own index (or primary key or unique constraint) that the statement ties to the parent's is dropped from the model, and the parent's is created on every partition. The name the partition's index had is not kept.
- `ALTER TABLE t { ENABLE | DISABLE | ENABLE REPLICA | ENABLE ALWAYS } { TRIGGER | RULE } name`: the trigger's or rule's firing mode. `{ ENABLE | DISABLE | ENABLE REPLICA | ENABLE ALWAYS } TRIGGER USER` sets the state of every trigger the project declares on the table, in any file order, and a statement naming one trigger overrides it; `TRIGGER ALL` does the same and also states the table's internal triggers, below. It is deployed after the trigger or rule is created, changed in place without dropping it, read back by `init`, and compared only when the project states one: a trigger or rule the project says nothing about keeps whatever mode the database has.
- `ALTER TABLE t { ENABLE | DISABLE } TRIGGER ALL`: every trigger on the table, **including the internal triggers PostgreSQL makes to enforce a foreign key** (those of the table's own foreign keys, and of foreign keys that reference it). The triggers the project declares take the state as with `TRIGGER USER`, so a statement naming one still overrides it. The internal triggers are not declared in a project, so their state is a setting of the table: `DISABLE` is deployed **at the end of the script**, after every table, key, and trigger exists (the internal triggers exist only once the foreign keys do), followed by the states of the declared triggers that differ from it, and `ENABLE` writes nothing for a new table. Only a superuser can change the internal triggers, so `publish --execute` runs it only with `--allow-superuser-statements` ([statements only a superuser can run](superuser-statements.md)). It is compared only when the project states it: a table the project says nothing about keeps whatever the database has, and a project that says `ENABLE TRIGGER ALL` enables internal triggers the database has disabled. `init` writes `DISABLE TRIGGER ALL` (followed by `ENABLE TRIGGER USER` when some declared triggers are enabled) for a table whose internal triggers are disabled. If a table's internal triggers are in mixed states, or in a state `ALL` cannot state (replica, always), `init` writes the most common one and warns, naming the table. A foreign key added later to a table whose internal triggers are already disabled gets enabled triggers, and pgproj does not notice while most of the table's internal triggers are still disabled; disable them by hand or recreate the state (`ENABLE TRIGGER ALL` first, then publish `DISABLE TRIGGER ALL`).
- `ALTER TABLE partition { ENABLE | DISABLE | ENABLE REPLICA | ENABLE ALWAYS } TRIGGER name` for a trigger the partition does not declare but its parent (or its parent's parent) does: PostgreSQL clones a row trigger onto every partition, and each copy has a firing mode of its own. The mode is kept on the trigger that is declared, by partition, written right after the trigger (a table before the partitions below it, since PostgreSQL sets those too), changed in place, and read back by `init` for each copy that is not enabled or differs from its parent's. A copy the project says nothing about keeps whatever mode the database has; a partition that does not descend from a table with that trigger is warned about, as a missing trigger is.
- `ALTER TABLE ONLY child ALTER COLUMN c { SET DEFAULT x | DROP DEFAULT }` for a column the child only inherits, from `INHERITS` or `PARTITION OF`: the child's own default. It is deployed as a statement right after the child's `CREATE TABLE`, changed in place, and read back by `init` when the live default differs from the parent's. Removing it gives the parent's default back.
- An index or key made on a partition **first** and attached to the parent's with `ALTER INDEX parent ATTACH PARTITION child`: PostgreSQL adopts an equivalent partition index when the parent's is created, so the partition's own name is kept. pgproj keeps such a partition index or primary/unique key when its name is not the one PostgreSQL would generate for a clone, creates it before the parent's, and `init` reads it back the same way; a partition index with the generated name stays the parent's, as before. The same holds for a partition's exclusion constraint made first and adopted by the parent's equivalent one (PostgreSQL 17 and later): it keeps a name other than the generated `<table>_<columns>_excl`, which `init` reads back (an exclusion constraint over expressions is always taken for the parent's).
- `ALTER TABLE t CLUSTER ON index` and `ALTER TABLE t REPLICA IDENTITY { DEFAULT | FULL | NOTHING | USING INDEX index }`. `CLUSTER ON` and `USING INDEX` name an index or a primary or unique key (an unnamed inline key by its default name, such as `t_pkey`) and are deployed right after it; `FULL` and `NOTHING` are deployed with the table. All are changed in place, read back by `init`, and compared only when the project states them, and only that they become so: a project that says nothing keeps whatever the database has. `ALTER TABLE t SET WITHOUT CLUSTER` says the table is clustered on no index: it is deployed only when the live table has a clustered index. A table the project says nothing about keeps its clustering, and a project that says both `CLUSTER ON` and `SET WITHOUT CLUSTER` for a table gets a warning and `CLUSTER ON` wins, because statement order across files is unknowable.
- A `CHECK` constraint a partition has under the name of one of its ancestors is the copy it inherits, and is not added a second time.
- `CREATE OR REPLACE VIEW` after a `CREATE VIEW` of the same name replaces it: `pg_dump` writes a view that other views depend on as a placeholder (`SELECT NULL::type AS col`) first, and the real body later.

Still reported and ignored: `SET STATISTICS`, `SET (storage parameters)`, `ALTER ... SET ACCESS METHOD`, and `DETACH PARTITION`.
