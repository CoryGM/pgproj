# Identity columns

How pgproj deploys and compares `GENERATED { ALWAYS | BY DEFAULT } AS IDENTITY` columns.

## What is deployed

The identity's options are deployed as you wrote them: `GENERATED BY DEFAULT AS IDENTITY (START WITH 10 INCREMENT BY 5)`.

## What is compared

- **Generation:** `ALWAYS` or `BY DEFAULT`, on the column.
- **Options:** only the ones you state (`START WITH`, `INCREMENT BY`, `MINVALUE`, `MAXVALUE`, `CACHE`, `CYCLE`). An option you leave out is
  PostgreSQL's default and isn't compared. The sequence's type follows the column's.

## Changes, made in place

| Change | Statement |
|---|---|
| Generation | `ALTER TABLE ... ALTER COLUMN ... SET GENERATED { ALWAYS \| BY DEFAULT }` |
| Identity added to a column | `SET NOT NULL` if needed, then `ADD GENERATED ... AS IDENTITY (options)` |
| Identity removed | `DROP IDENTITY`, then `DROP NOT NULL` if the column allows nulls |
| A stated option | `ALTER TABLE ... ALTER COLUMN ... SET INCREMENT BY 5 SET START WITH 20 ...` |

- **A changed `START WITH`** is recorded with `SET START WITH`, which doesn't move the counter. pgproj never restarts an identity's sequence:
  restarting it could hand out values the column already holds. An ordinary sequence's changed `START` is the same: `ALTER SEQUENCE ... START WITH`,
  never `RESTART`.
- **Identity added to a column that has rows:** PostgreSQL starts the new sequence at its start value. When you state no `START WITH` and
  the identity counts up, pgproj moves the sequence past the column's largest value (`setval`), so the next row can't collide.
- **Dropping an identity** keeps the column's values, so `publish --execute` doesn't count it as destructive. Its sequence goes with it.

## `init`

`init` writes an identity's options on its column, only those that aren't PostgreSQL's defaults for the type and direction. It doesn't write
the identity's sequence as a `CREATE SEQUENCE` of its own.

## Known limits

- An identity sequence's own name (`SEQUENCE NAME`) isn't read; pgproj assumes PostgreSQL's `<table>_<column>_seq`.
- A comment or grant on an identity's sequence isn't read from the database.

An identity's sequence is logged or unlogged with its table (see [sequences](supported-objects.md)). `UNLOGGED` or `LOGGED` among the identity's options, `GENERATED ALWAYS AS IDENTITY (UNLOGGED)` (PostgreSQL 15 and later), sets it the other way, as `pg_dump` writes a sequence that was changed on its own. The word is deployed as written, read back by `init` when the sequence's persistence differs from its table's, and compared only when the column states it; a change is `ALTER SEQUENCE ... SET LOGGED|UNLOGGED`, which keeps the counter. PostgreSQL 14 does not accept the words, so a project that states one cannot be published there.
